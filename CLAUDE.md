## Project context

**Lumi** (repo `Projet-Lumiere.s`) is a personal webapp that aggregates movie showtimes from 6 Lyon cinemas onto a single page, so the user doesn't have to check each cinema's site by hand (particularly useful for spotting re-releases of old films).

**This is the user's first web project and first contact with JavaScript.** They are a beginner in web dev — explain concepts simply with concrete examples before coding, and guide step by step rather than writing everything at once. They work on Windows, in VS Code, using PowerShell as the terminal.

Three living docs in `docs/` are updated as the project progresses and hold more detail than this file:
- `docs/fiche-etat-du-projet.md` — condensed, self-sufficient project status snapshot (stack, data formats, what's done, next steps)
- `docs/fiche-methode.md` — step-by-step setup log with exact commands run so far
- `docs/fiche-roadmap.md` — Phase 1 / Phase 2 checklist and undecided items

## Architecture

- Single Flask server (`app.py`) serves both the API and the frontend — no separate frontend build/server.
- `CINEMAS` dict in `app.py` maps display names to Allociné cinema IDs. `/api/seances` reads an optional `jour` query param (`request.args.get("jour", date.today().isoformat())`, e.g. `/api/seances?jour=2026-07-29`), then loops over `CINEMAS` and, per cinema, combines two sources into one dict grouped **by film title** (not by cinema): `get_seances_detaillees()` (a custom function, see below) for showtimes, and `api.get_movies(id, date)` for the poster URL (`urlPoster`) and release date. Result shape: `{ "Film title": { "poster": url, "dateSortie": "YYYY-MM-DD" | null, "seances": { "Cinema name": [showtime, ...] } } }`, where each showtime also carries `lienReservation` (see below). `dateSortie` comes from `date_sortie_la_plus_ancienne()`, which takes the earliest date across a film's `releases` list from `get_movies()` (a film can have multiple releases — original run, re-release — and the app cares about the original one, for spotting re-releases of old films); `null` when no release has a date.
- `get_seances_detaillees()` in `app.py` reimplements `allocineAPI.get_showtime()`'s internal pagination/dedup logic by calling the library's private helpers directly (`api._get_json_request`, `URLs.showtime_url`), because the public `get_showtime()` discards the `projection`/`experience` fields (screening format — standard/IMAX/4DX) and the `data.ticketing` field (booking URLs) that this app needs. This is a deliberate trade-off: relying on underscore-prefixed "private" library internals is more fragile to library updates than using its public API. It skips any `results` entry whose `movie` is `None` (a latent bug found once the app started requesting many more day×cinema combinations than before — the library's own `get_movies()` already guards against this). Each showtime's `lienReservation` comes from `lien_reservation()`, which reads `data.ticketing` (a list of booking options per showtime) and prefers the `"default"` provider (direct cinema link) over `"relay"` (third-party tracking link); `null` when no booking option exists yet.
- `films_dun_jour(id_cinema, jour)` combines `get_seances_detaillees()` (showtimes) and `api.get_movies()` (poster, release date) for one cinema/day into `{ title: {poster, dateSortie, seances} }`, and is the shared building block behind both `/api/seances` (looped over all 6 cinemas for one day) and `/api/films-periode` (see below). It carries a lightweight in-memory cache — a module-level dict `cache_films_jour` keyed by `(id_cinema, jour)`, entries valid for `DUREE_CACHE` (1 hour) — added after live testing hit Allociné's `429 Too Many Requests` on multi-day requests; it resets on every server restart (including Flask's autoreload on save) and is a stopgap ahead of the real background-caching plan (V3, once permanent hosting exists). `/api/films-periode?semaines=1|2|3&cinemas=<comma-separated cinema names>` (V2) loops `semaines*7` days × the selected cinemas (all 6 if `cinemas` is absent; an explicit empty value means none) and returns the deduplicated set of films appearing in that window, each with `{poster, dateSortie, joursDiffusion}` where `joursDiffusion` is `{ "YYYY-MM-DD": { "Cinema name": [showtime, ...] } }` — one entry per day the film actually plays, built by calling `films_dun_jour()` per cinema/day (so it shares the cache with `/api/seances`) rather than `api.get_movies()` alone, since the per-day showtime breakdown needs the full showtime data. A `print(f"Récupération : {nom_cinema} - {jour}")` inside the loop is deliberately kept (not just debug scaffolding removed later) — it gives visible progress in the terminal during a request that can take a while (up to 42 live calls for one week × 6 cinemas), which matters because there's no error handling on the frontend's `fetch()` calls (see below) to otherwise indicate the request is still alive rather than hung.
- Frontend period mode: `modeActuel` (`"jour"` | `"periode"`) is a module-level flag in `script.js` that `mettreAJourAffichage()`, `activerFiltreCinema()` and the two loader functions (`chargerSeances()`, `chargerFilmsPeriode()`) branch on. The `#jour` day-picker and `#periode` week-count `<select>` (grouped together in `.recherche-date`, stacked via `flex-direction: column`, both styled/sized alike — `width: 200px; box-sizing: border-box` — to line up) are mutually exclusive — each one's `change` handler clears the other's value before loading. In `"jour"` mode, the cinema checkboxes filter client-side (`obtenirFilmsFiltres()`) against already-fetched data; in `"periode"` mode, filtering happens server-side (checkbox changes re-`fetch` `/api/films-periode` with the updated `cinemas` list, built via `obtenirCinemasCoches()` + `.join(",")` + `encodeURIComponent()`), since `/api/films-periode` doesn't return `dateSortie`'s sibling `seances` field at all — it returns `joursDiffusion` instead (see above). `afficherFilms()`/`activerClics()` branch on three shapes: a film with `seances` renders as the existing per-cinema clickable card (Phase 1, jour mode); one with `joursDiffusion` (period mode) renders via `genererJoursHTML()` as a list of `.jour-item`s (one `.jour-titre` + hidden `.jour-horaires` per day the film plays, dates sorted via `Object.keys(...).sort()` since `YYYY-MM-DD` sorts alphabetically = chronologically); a film with neither gets skipped (`continue` in `activerClics()`). Clicking a `.film` card toggles whichever of `.horaires`/`.jours` it has (`const zoneAOuvrir = horaires || jours`); within an open `.jours` list, `activerAccordeonJours()` gives each `.jour-titre` its own click handler that calls `event.stopPropagation()` (so it doesn't also toggle the parent `.film` card), then closes every `.jour-horaires` sibling under the same film before reopening the clicked one (single-day-open accordion) — `.parentElement` is used twice to walk from the clicked title up to its `.jour-item` and then to the shared `.jours` container. `afficherChargement(avecAvertissement)` renders the loading state; passing `true` (only `chargerFilmsPeriode()` does) appends a small warning paragraph below it about slow multi-week/multi-cinema searches — both live inside one `.etat-chargement` wrapper so they stack normally and don't get sliced into separate grid cells by `#seances`'s `display: grid`, and the warning simply disappears on its own once `afficherFilms()` overwrites `#seances`'s content (no separate show/hide state to manage). **Known gap**: no `fetch()` call anywhere in `script.js` has error handling (no `.catch()`, no `response.ok` check) — a failed request (seen in practice: Allociné dropping the connection under heavy load, or a local security tool like Avast's web shield killing a long-held connection) leaves the page stuck on the loading message indefinitely with no feedback.
- Frontend is vanilla HTML/CSS/JS (deliberate — this is the user's JS learning ground, guide new concepts step by step in chat rather than editing their files directly — see workflow note below). `templates/index.html` is the static shell: a `.entete` div holds the logo (`static/images/logo.png`, `position: absolute` anchored to `.entete`'s `position: relative`) and the `<h1>` title, plus two Google Fonts `<link>` tags (Lobster Two for the title, Germania One for the subtitle — chosen over a locally-installed-only font so they render for every visitor), plus a `.barre-outils` div holding the cinema filter (`#bouton-filtre` toggles a `.liste-cinemas` checkbox list, all checked by default — floated over the film grid via `.filtre-cinema { position: relative }` + `.liste-cinemas { position: absolute; z-index: 10 }`, checkboxes recolored via `accent-color` rather than a full custom-appearance rebuild), a sort `<select id="tri">` (options: default / release date ascending / descending), and the `<input type="date" id="jour">` day-picker — all three styled to the LUMI palette. `static/script.js` fetches `/api/seances` (optionally `?jour=...` when the day-picker's `change` event fires), first calling `afficherChargement()` to reset `#seances` to the loading message so stale results don't linger during the request, into `dernieresDonnees` (module-level cache, avoids refetching on filter/sort changes), then `mettreAJourAffichage()` is the central render path: `obtenirFilmsFiltres()` keeps only films present in a checked cinema, `trierFilms()` sorts by `dateSortie` (films with a `null` date always sort first, regardless of direction — deliberate "when in doubt, surface it" choice) unless `tri` is `"defaut"`, then `afficherFilms()` renders the grid (poster + title) via `document.getElementById("seances").innerHTML` and rewires the per-film click listeners (`activerClics()`, needed again each render since `innerHTML` destroys the old DOM nodes) that toggle a hidden per-cinema showtimes list (`style.display`), each showtime annotated with VF/VO (from `diffusionVersion`) and projection format (from `projection`/`experience`), wrapped in a `target="_blank" rel="noopener"` link to `lienReservation` when one exists (plain text otherwise). `static/style.css` implements the "LUMI" palette (navy background, turquoise/cream/gold accents): a responsive `display: grid` film grid, card hover effect (`transform`/`box-shadow`/`transition`), styled headings/lists, and the reservation link styled to inherit the showtime's own color/font (`.horaires li a { color: inherit; ... }`) rather than the browser's default blue/underline.
- Data source: the `allocine-seances` PyPI package (`allocineAPI.allocineAPI`, from GitHub `lefevre-dev/AllocineAPI`), an unofficial wrapper around Allociné's internal GraphQL API. Despite the package name suggesting JS, it's a Python library. Its data is live — showtime listings can change between two requests (e.g. a session becomes unbookable and disappears); don't assume a missing entry is a code bug without comparing raw JSON across two points in time first.
- `explore.py` is a throwaway sandbox script used to explore the `allocineAPI` library interactively (finding cinema IDs, inspecting raw response shapes via the library's private request helpers) — not part of the app itself, frequently rewritten in place.

### Known limitation

Only one day at a time can be viewed (via the day-picker or `?jour=`) — no way yet to browse a date range at a glance. A "multi-week overview" idea is noted in the roadmap doc but deliberately deferred: Allociné's API only accepts one exact date per call, so covering several weeks live would mean one call per day per cinema (100+ requests) — likely needs a periodic background fetch/cache instead of a live request, possibly sharing infra with the Phase 2 alert cron job.
